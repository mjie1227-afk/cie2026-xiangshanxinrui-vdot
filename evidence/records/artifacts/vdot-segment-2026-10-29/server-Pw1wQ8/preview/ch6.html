香山整核集成与关键控制路径

本文要点

  • vdot.vv 保持向量指令分类，以单 uop 接入 VFEX0，复用既有源读取、唤醒和退休路径。
  • oldVd 作为显式源依赖，使合法 VL=0 的新物理目的获得完整旧值。
  • 取消由流水有效位、完整 ROB 身份和后端恢复共同处理；完成、物理写入与退休是不同事件。
  • mtval 修复通过 ROB 保存并重建故障指令字段，恢复新增指令与所选参考模型的一致性。
  • 代表性波形验证了发射前共享端口竞争和退休侧 VS-dirty 请求，具体读数见第 7 章。

2 方法

2.1 单 uop 与旧目的依赖

一条 vdot.vv 由一个 uop 承担八项点积。 以下为保存的 DecodeUnit.scala 摘录：

  when(inst.isVdot) {
    io.deq.isComplex := true.B
    io.deq.uopInfo.numOfUop := 1.U
    io.deq.uopInfo.numOfWB := 1.U
    io.deq.uopInfo.lmul := 1.U
  }

isComplex 保留向量复杂译码属性；numOfUop 和 numOfWB 限定该指令的内部拆分。uopInfo.lmul 是微操作信息字段，合法 LMUL=1 在 vtype.vlmul 中的编码为 0，两者属于不同表示。

译码在 isDependOldVd 条件中加入 inst.isVdot。例如，逻辑 v3 原先映射 P10，本次重命名分配 P51；合法 VL=0 时，执行端把 P10 的值传给 P51，退休后保持架构 v3 的原内容。单纯关闭写使能会留下未获得旧值的新物理目的，因此保持路径仍需要源就绪、执行和退休。

证据：DecodeUnit.scala

2.2 投机取消与后端恢复

VDot 用完整 ROB 指针的 needFlush 判断较老 redirect 是否覆盖本指令。指针包含 flag、value；判定还使用 redirect 的有效位和 level。末级输出门控为：

io.out.valid := fixValidVec.last && !outCtrl.robIdx.needFlush(io.flush)

结果输出前到达的取消由流水有效位与门控处理。若较老分支在结果已经物理写入后才纠正路径，ROB 与重命名恢复使该结果不进入已提交架构状态。

2.3 执行期异常与 mtval 信息通路

修复在 ROB 分配时保留指令编码，并在对应指令发生精确异常时送往 CSR。 短 VL 的非法状态由执行单元发现，原有译码期异常信息通路没有为这条指令保存可用的完整指令字。新增 VdotTrapInstTable 用 ROB 槽位关联编码与动态身份：

  val isVdot = RegInit(VecInit(Seq.fill(RobSize)(false.B)))
  val generation = Reg(Vec(RobSize, Bool()))
  val fields = Reg(Vec(RobSize, UInt(16.W)))
  for (a <- io.alloc) {
    when(a.valid) {
      val idx = a.bits.robIdx.value
      isVdot(idx) := VdotInstructions.VDOT_VV === a.bits.instr
      generation(idx) := a.bits.robIdx.flag
      fields(idx) := Cat(a.bits.instr(25), a.bits.instr(24,20),
                        a.bits.instr(19,15), a.bits.instr(11,7))
    }
  }
  val f = fields(io.head.value)
  val word = Cat(0.U(6.W), f(15), f(14,10), f(9,5), 0.U(3.W), f(4,0), "h0b".U(7.W))
  val matched = isVdot(io.head.value) && generation(io.head.value) === io.head.flag
  // Same one-cycle capture as Rob.io.exception; no writeback-order arbitration.
  io.out.valid := RegNext(io.trap && io.illegal && !io.interrupt && matched, false.B)
  io.out.bits := RegEnable(word, io.trap)

fields 取 vm、vs2、vs1、vd 共 16 个可变位，重建时补回固定的 funct6、funct3 和 opcode 0x0b。isVdot 区分指令类型，generation 与 ROB flag 一起区分循环复用的槽位，因此每槽共保存 18 位；MinimalConfig 的 48 个槽位对应 864 个存储字段位。

io.head 指向发生精确异常的队首指令。trap && illegal && !interrupt && matched 选择属于该动态 VDot 的非法指令异常，并与 ROB 的异常信息同步寄存。CSR 侧通过以下选择逻辑接收重建指令；其他异常继续使用原有 trapInstMod 通路：

  csrMod.io.trapInst := xiangshan.backend.rob.VdotTrapInstSelect(
    csrIn.exception.valid, csrIn.exception.bits.isInterrupt,
    csrIn.exception.bits.exceptionVec(EX_II), csrIn.exception.bits.vdotTrapInst,
    trapInstMod.io.currentTrapInst)

这条信息路径依次为“ROB 分配保存编码 → 队首精确异常匹配 → 重建指令字 → CSR 选择 → mtval”，与执行结果的先后写回顺序无关。

非法指令陷阱是否向 mtval 提供故障指令位，是 RISC-V 特权规范允许的实现选择。修复目标是新增指令与本实验参考模型在该字段上的一致性。差分失败、故障定位与修复后回归完整列于第三阶段的 NEMU 与 DiffTest 报告。

证据：VdotTrapInst.scala · CSR.scala · NEMU 与 DiffTest 报告 · RISC-V 特权规范

2.4 共享端口与退休侧 CSR 请求

VDot 所在 VFEX0 与 VIOTA 所在 VFEX1 共用 VfWB 端口 0 的发射前仲裁资源。发射前申请用于安排执行后的资源占用；实际结果写回仍是后续单独的事件。两层观测在第 7 章分列。

VS-dirty 请求按 isCommit AND OR(commitValid[i] AND dirtyVs[i]) 聚合各退休槽贡献，再经寄存送往 CSR。只有被选为有效退休的指令参与聚合，槽中残留的 dirtyVs=1 数据位本身不产生请求。

4 总结与实验边界

VDot 通过向量译码、显式 oldVd 依赖、固定延迟配置和精确异常通路接入整核。正常执行、完成后取消、退休侧 CSR 请求和选定端口竞争均有对应动态实例。

  • 当前结果对应固定 MinimalConfig 和所列场景；不同取消时刻或其他 FU 组合需分别验证。
  • CSR 波形覆盖退休贡献到 CSR 接收请求；最终 VS 状态与所有优先级交互属于另一层状态检查。
  • 已确认的竞争位于发射前仲裁层；该窗口的实际结果写回层未出现共同请求。
