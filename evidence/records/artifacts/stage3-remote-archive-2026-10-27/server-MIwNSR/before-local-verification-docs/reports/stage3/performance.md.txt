## 2 为什么需要显式计时边界

锁定源码中，CSR指令初始译码有waitForward/blockBackward控制，但Rename依据CSROoORead列表对普通只读CSR放宽次序，mcycle/minstret不在保留顺序列表。因此仅前后放只读计数器访问不足以作为本项目的完成边界依据。

预检使用CSRRW写mscratch作为边界：该形式不属于只读CSR优化，保留等待前序/阻止后序的调度控制。区间外先排空初始化工作，区间后阻止取证存储越过结束读数；内区间四次写边界分别隔离计数器和负载。mscratch入口值保存在t6，函数返回前恢复并自检。相关DecodeUnit/Rename/CSROoORead/NewDispatch/MachineLevel源码哈希在包内锁定，不修改核心或计数器值。

```text
外侧边界 → C0 → 边界 → I0 → 边界 → 负载 → vmv.x.s消费者
         → 边界 → I1 → 边界 → C1 → 外侧边界 → 记录/恢复
```

C0/C1读取mcycle，I0/I1读取minstret。消费者依赖结果v3，并检查低字节为36；完整128位结果另行存储检查。原始周期差包含四个内部边界、两个minstret读取和消费者，全部保留。空负载用于评估这一公共成本，不自动相减或直接给出纯FU延迟。

计数含义依据[RISC-V计数器规范](https://docs.riscv.org/reference/isa/v20260120/unpriv/counters.html)；CSR读取退休计数时观察本指令执行前的值，见[Zicsr规范](https://docs.riscv.org/reference/isa/unpriv/zicsr.html)。结合固定汇编区间，预期退休增量为负载指令数+4：起始minstret读、两道内部边界及消费者；结束minstret读本身不计入该读值。

## 5 完整操作依赖链：方法与实测结果

### 7.1 实际耗时与全程计数线索

保存的result.json阶段记录显示应用构建3.525秒、architecture运行1651.336秒（27分31.336秒），两阶段退出0。这是宿主墙钟耗时；3600秒为运行上限，表4为客体处理器周期，三者不可互换。阶段耗时之和也不代表包含全部检查/包装操作的总命令耗时。
