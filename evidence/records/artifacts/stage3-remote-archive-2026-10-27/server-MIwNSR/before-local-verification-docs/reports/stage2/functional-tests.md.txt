## 6 分支投机路径的窗口取证

### 6.1 输入与方法

使用同一emu、源码NEMU、Flash、`vdot-cancel-csr`镜像和seed1。文本定位选取第9次目标分支附近，保存6978～9258范围的双边沿VCD，运行到10000周期停止。波形为457224402字节，时间单位1ps，时间戳14060～18621。该运行用于取证，不是性能测量。

解析器按上升沿前稳定值检查握手，以PC/机器码、完整ROB flag/value和pdest关联事件；所有rename握手参与ROB身份复用检查。分析退出0，原波形未改动。本次已归档的是用户回传摘要，完整事件JSON仍在服务器。[UbYWTP核验](../../artifacts/vdot-window-events-2026-10-25/server-UbYWTP/review.json)；[fgpWCe补证与单例验收](../../artifacts/vdot-window-supplement-2026-10-25/server-fgpWCe/review.json)。补证通过锁定源码的EXU/Dispatcher组合连线恢复入口身份，输入valid/ready仍来自实际FU，并要求父EXU接受条件一致。

整个采样窗口中，时钟高/低相位的`VCD时间−2×timer`分别为98/99，`VCD时间−2×cycleCnt`分别为102/103。这建立本次记录的计数器关系；以下直接使用VCD时间戳，避免将不同计数器混用。

### 6.2 正常执行对照

8个VDot实例都观察到rename、FU输出握手、控制侧写回和ROB提交。例如target1：PC=0x80000208、机器码0x0220818b、ROB=1/36、pdest=62，在14208重命名、14220输入握手、14224完成、14272提交。结果先完成、随后按程序顺序提交，说明两者不是同一时刻。

还观察到更早的一组target16/17被ROB1/24的redirect覆盖并随后复用。target17与target19均出现pdest61，但完整ROB不同，不能合并为同一动态指令。补证显示target17在16872有输入握手，同一时间出现另一redirect，随后没有输出和提交。尚未逐拍关联其本地flush到达时序，因此该实例另行保留，不能写成“发射前取消”。

### 6.4 九次身份拒绝的解释

拒绝全部来自分支target0、2、4、6、8、10、12、14、18，端口均为`io_toCtrlBlock_writeback_5`。每次完整ROB与该分支匹配，分析器期望的pdest为rename记录中的0，实测字段为null。null表示没有取得该字段，不是硬件输出了不同的目的寄存器编号。

原关联器为所有目标统一要求ROB和pdest，适用于有向量目的的VDot，却使这一分支完成观察被保守拒绝。分支没有向量目的写入，不能把占位pdest0解释为必须在所有分支通路出现的有效目的。9次拒绝中没有VDot目标，也没有“两个非空pdest数值不同”的情况。保留原始计数与诊断，不把null改成0以消除拒绝。

### 6.5 已关闭范围与剩余覆盖

已关闭ROB1/27、pdest61这一动态实例的执行完成后取消验收，以及9次拒绝的分析器解释。目标PC重复出现时仍需完整ROB及生命周期约束，不能仅用pdest或PC合并。

退休驱动CSR请求现已通过第6.6节检查，下一主项转向多FU实际端口竞争。WB输入ready未采得的观测限制仍保留，但不阻塞已由其他独立事件闭合的取消案例。最终mstatus/vsstatus逐拍状态及全部CSR副作用仍未作完整覆盖。

### 6.6 退休到CSR的VS-dirty请求

复用同一Cpa0HX波形，核对2280个非复位ROB上升沿；没有跳过复位沿，首个缺少沿前样本的边界不计入。依据锁定源码，沿前退休贡献为：

```text
expected = isCommit AND OR(commitValid[i] AND info[i].dirtyVs)
```

`GatedValidRegNext(Bool)`为RegNext，因此比较沿后ROB dirty_vs与沿前expected，再比较沿后CSR接收请求。aReAEz检查零差异、脚本/tee退出0；8个正常VDot的提交身份均匹配且贡献为1，target19没有提交贡献。[回传核验](../../artifacts/vdot-csr-commit-window-2026-10-25/server-aReAEz/review.json)。

| VCD时间 | 退休情况 | 沿后ROB / CSR请求 | 说明 |
|---:|---|---|---|
| 14272 | 分支dirtyVs0与VDot dirtyVs1同拍退休 | 1 / 1 | 聚合请求由同拍VDot贡献，不能只看分支字段 |
| 15598 | 仅分支ROB0/31退休，dirtyVs0 | 0 / 0 | 分支本身不产生VS-dirty请求 |
| 15600 | VDot ROB0/32退休，dirtyVs1 | 1 / 1 | 两拍相邻观察可区分分支和VDot贡献 |
| 16904、16908 | target19发射/完成时无有效退休贡献 | 0 / 0 | 完成本身不触发此提交请求 |
| 16952 | 目标redirect时无有效退休贡献 | 0 / 0 | 已取消候选不成为请求来源 |
| 16958 | 分支ROB1/26退休，dirtyVs0 | 0 / 0 | 同PC候选未随分支提交 |

本项验证的是“退休条件→ROB寄存请求→CSR接收端”。此前40例套件另有架构CSR自检；两者共同增加控制证据，但不等同于逐拍观察mstatus/vsstatus最终VS状态、所有软件CSR写入优先级或全部异常副作用。接下来优先补混发实际竞争，而不是反复重验这一请求通路。

### 6.8 共享端口竞争定向验证
