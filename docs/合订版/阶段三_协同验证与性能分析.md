# 7 NEMU 扩展与差分验证

本项目已在 NEMU 中加入 vdot.vv 的译码和执行语义，并完成参考库接口检查与 RTL/NEMU 整核协同验证。参考模型 API 通过 268 例，另有 10 例因配置不适用单列；修复版整核的 SMOKE、EXCEPTION、OVERLAP 和 PIPELINE 套件全部通过。

## 7.1 NEMU 与 RTL 共用 v0.1 指令规格

参考模型与 RTL 遵循同一份项目 v0.1 指令规格，合法配置范围和状态更新规则一致〔1〕。

在向量执行权限可用的前提下，合法配置要求 vill=0、SEW=8、LMUL=1、vstart=0，VL 为 0 或 8～16，vtype 保留高位为零。合法非零 VL 固定计算源低八项，精确和写入低 32 位、高 96 位清零；合法 VL=0 保持完整旧目的。类型、权限和重启条件的检查排在长度分支之前。

RTL 基于 XiangShan 16ae9ddc，叠加 VDot 和异常修复；参考模型基于 NEMU a48a11f2，叠加独立的语义实现。完整版本和二进制文件校验值见阶段三复现索引。

## 7.2 custom-0 译码规则与 def_EHelper(vdot)

NEMU 的改动包括译码入口、执行 ID 注册、头文件接入和新增语义函数。custom-0 的末七位为 `0001011`，funct6 和 funct3 为零，其余字段解析 vm 及寄存器编号。译码规则如下：

```c
#ifdef CONFIG_RVV
  def_INSTR_IDTAB("000000 ? ????? ????? 000 ????? 00010 11", OP_V  , vdot);
  def_INSTR_IDTAB("??????? ????? ????? ??? ????? 10101 ??", OP_V  , OP_V);
#endif // CONFIG_RVV
```

第一条规则匹配 custom-0 编码，告诉 NEMU 执行 vdot；第二条保留原有的标准 OP-V 处理。新增执行 ID 注册在 isa-all-instr.h，vcompute.h 引入 vdot.h。这样，NEMU 识别机器码后，就能调用 `def_EHelper(vdot)` 执行对应规则。

执行函数如下，摘自 vdot.h 源码[〔2〕](<../../src/NEMU/src/isa/riscv64/instr/rvv/vdot.h>)：

```c
def_EHelper(vdot) {
  require_vector(true); // host/guest VS and vill, before the vl=0 path
  if ((vtype->val >> 8) != 0 || vtype->vsew != 0 || vtype->vlmul != 0 ||
      vstart->val != 0 || (vl->val != 0 && (vl->val < 8 || vl->val > 16))) {
    longjmp_exception(EX_II);
  }
  const uint32_t word = s->isa.instr.val;
  const unsigned vd = (word >> 7) & 31;
  const unsigned vs1 = (word >> 15) & 31;
  const unsigned vs2 = (word >> 20) & 31;
  const unsigned vm = (word >> 25) & 1;
  if (vl->val != 0) {
    // Snapshot before any write, including vd=v0 and all source overlaps.
    const uint64_t a = cpu.vr[vs1]._64[0];
    const uint64_t b = cpu.vr[vs2]._64[0];
    const uint64_t mask = cpu.vr[0]._64[0];
    int32_t sum = 0;
    for (unsigned i = 0; i < 8; ++i) {
      const int ai = ((int)((a >> (8*i)) & 255) ^ 128) - 128;
      const int bi = ((int)((b >> (8*i)) & 255) ^ 128) - 128;
      if (vm || ((mask >> i) & 1)) sum += ai * bi;
    }
    cpu.vr[vd]._64[0] = (uint32_t)sum;
    cpu.vr[vd]._64[1] = 0;
  }
  vstart->val = 0;
  vp_set_dirty(); // includes legal vl=0 and guest VS when virtualized
}
```

实现中有三处与边界测试直接相关：

- 合法性检查位于 VL=0 之前，空操作也不能绕过异常条件。
- 两个源和掩码先存入局部变量，再改写目的；vd 与源或 v0 重叠时仍读取旧值。
- `(uint32_t)sum` 写入低 64 位容器时高 32 位为零，另一个 64 位字也置零，恰好形成低 32 位结果与高 96 位零。

合法 VL=0 跳过目的更新，但仍执行成功路径的状态处理；`vp_set_dirty()` 复用 NEMU 已有的向量状态机制。源文件及译码入口统一保存在 NEMU 修改快照中[〔3〕](<../../src/NEMU>)。

## 7.5 执行期非法异常的 mtval 失配与修复

短 VL 用例曾发现一个异常信息错误：RTL 正确报告了非法指令，却没有把故障机器码写入 mtval。NEMU 的 mtval 有正确编码，因此 DiffTest 能报出差异。补上机器码传递通路后，原来的 64 个异常用例全部通过。下面按现象、原因、修改和复测说明。

### 7.5.1 现象：DUT 的 mtval 为零

早期 emu 执行短 VL 用例 short-1-vm0 时，短 VL 按规格触发非法指令异常，但 DiffTest 报告：

```text
mtval different at pc = 0x0080000218, right=0x0020818b, wrong=0
```

参考模型的 mtval 为故障机器码 `0x0020818b`，DUT 的 mtval 为零。结合反汇编和提交轨迹可以区分两个 PC：`0x80000218` 是前一条已提交的 `sd t0,40(s0)`，实际发生异常的 VDot 位于 `0x8000021c`。异常同步时，差分行保留最近的比较位置，`mepc=0x8000021c` 则精确记录了故障指令地址。

![参考模型记录故障指令地址和指令字](<../assets/stage2/mtval-before-reference.png>)

图 7-2　参考快照为 mcause=2、mepc=0x8000021c、mtval=0x0020818b。

![DiffTest发现DUT与参考mtval不同](<../assets/stage2/mtval-before-difference.png>)

图 7-3　DUT 的 mtval 为零，参考值为故障机器码，差分检查随后中止运行。

### 7.5.2 原因：执行期非法异常拿不到指令字

VL=1 的非法条件是在执行期判断出来的。原有 trapInstInfo 主要传递译码期发现的非法指令，VDot 到达 ROB 队首时，异常类型已经送到，匹配的机器码却没有跟上，因此 mtval 读到零。需要修复的是故障指令信息通路。

### 7.5.3 改法：ROB 分配时保存可变编码字段和代际，队首重建指令字

修复后，ROB 在分配槽位时保存 VDot 的可变编码字段和代际。发生队首异常时，先确认槽位中的记录属于本次指令，再拼回机器码，交给 CSR 选择器。异常仲裁和 NEMU 语义保持原样，新增通路补上执行期异常所需的指令字。字段组成和容量见第 5 章 5.5。

### 7.5.4 回归：原异常用例 64 例 EXCEPTION 全部通过

修复生成新 emu 后，我们用原异常镜像与参考库配置回归：64 例 EXCEPTION 全部通过，随后 OVERLAP、SMOKE、Hello 与 VADD 也通过。原失败 emu 和日志保留用于追溯，成功结果对应修复后的仿真器版本。

# 8 标准 RVV 等价基线

RVV-m1、RVV-mf2 两条标准向量指令组合已完成与 VDot 的等价检查：144 种输入配置、432 次内核调用的结果和指定状态一致，本地参考执行、完整 C 检查及服务器 RTL/NEMU 协同运行均通过。

公平比较周期前，先让三条实现完成同一件事：算出相同点积，得到相同的完整目的寄存器，VL=0 时保留旧目的，并在返回时恢复约定的配置。本章说明怎样用标准 RVV 指令完成这些操作，以及怎样核对三条实现的结果。

## 8.1 kernel_end 比较点与寄存器约定

三条实现都执行到汇编标签 `kernel_end` 再比较状态。此时核心计算已经结束，测试程序还没有为存储结果而重新配置向量。入口统一为合法 M 态、e8/m1、vstart=0，向量状态可用。

调用约定中，v0 放掩码，v1/v2 放两个源，v3 接收结果。v8/v9/v16 和 t0 留给实现临时使用，调用者不要求它们保持原值。测试在 `kernel_end` 检查约定需要保持的寄存器和状态，随后才存储结果。

每条实现先与独立算出的期望值比较，再与另外两条实现比较。这样能发现某条实现单独出错，也能检查三条实现是否一起算成了同一个错误答案。这套调用约定用于性能对比。源与目的寄存器任意重叠、非法配置等情况，由第 7 章的定向套件另行检查。

## 8.2 vwmul.vv 加 vwredsum.vs：两次加宽得到 INT32

标准 RVV 分两步计算：`vwmul.vv` 把两组 INT8 相乘，得到 INT16 乘积；`vwredsum.vs` 再把八个 INT16 乘积相加，得到 INT32 和。归约种子，也就是求和的起始值，设为零。计算前先把 v3 全部清零；归约时采用尾部保持策略，让低 32 位接收总和，其余位仍为零。

乘法和归约的元素宽度不同，需要切换 SEW/LMUL。在 VLEN=128 时，八个 INT8 只占半个向量寄存器。RVV-m1 按 m1 配置乘法，加宽后的目的使用 v8/v9 这一组；RVV-mf2 从 mf2 开始，加宽后恰好使用一个 m1 的 v8。两条基线计算相同的八项点积，保留它们是为了比较不同寄存器分组的执行成本。

表 8-1　两条基线的乘法与归约配置

| 基线 | 乘法配置 | 乘积存放 | 归约配置 |
| --- | --- | --- | --- |
| RVV-m1 | e8/m1，VL=8 | EMUL=2，v8/v9 | e16/m2，VL=8 |
| RVV-mf2 | e8/mf2，VL=8 | EMUL=1，v8 | e16/m1，VL=8 |

乘法生成完整的有符号乘积，掩码在归约时选择有效项。VL=0 跳过计算并保留旧目的，末尾恢复调用者的 vl/vtype。标准指令行为依据 RVV 1.0 规格，实际实现以本项目汇编为准[〔11〕](<../../apps/vdot-rvv-equiv-v1/cases.S>)。

## 8.3 三条核心段：1 条对 9 条静态指令

在本章调用约定下，VDot 核心段为一条自定义指令，两条 RVV 基线的非零路径各为九条静态指令。下文列出具体代码；周期成本在第 9 章测量。

共同测试壳已装入源、掩码和入口配置，a3/a4 分别保存原 VL/vtype。下面列出 vm=0 的三个核心段。

VDot 由单条自定义指令完成：

```asm
    .word 0x0020818b
```

该字对应 `vdot.vv v3,v2,v1,v0.t`，操作数顺序为 vd、vs2、vs1。

RVV-m1 显式完成分支、配置、乘法、清零、归约和恢复：

```asm
    beqz a3,rvv_m1_vm0_restore
    vsetivli zero,8,e8,m1,tu,mu
    vwmul.vv v8,v1,v2
    vsetivli zero,4,e32,m1,tu,mu
    vmv.v.i v3,0
    vmv.v.i v16,0
    vsetivli zero,8,e16,m2,tu,mu
    vwredsum.vs v3,v8,v16,v0.t
rvv_m1_vm0_restore:
    vsetvl zero,a3,a4
```

RVV-mf2 改变乘法和归约的分组，其余职责相同：

```asm
    beqz a3,rvv_mf2_vm0_restore
    vsetivli zero,8,e8,mf2,tu,mu
    vwmul.vv v8,v1,v2
    vsetivli zero,4,e32,m1,tu,mu
    vmv.v.i v3,0
    vmv.v.i v16,0
    vsetivli zero,8,e16,m1,tu,mu
    vwredsum.vs v3,v8,v16,v0.t
rvv_mf2_vm0_restore:
    vsetvl zero,a3,a4
```

在 e32/m1、VL=4 下，`vmv.v.i` 将目的 v3 和归约种子 v16 完整清零。切换配置后，`vwredsum.vs` 把和写入 v3 的第一个 32 位元素，tu 让剩余位保留先前的零。最后 `vsetvl` 恢复入口 VL/vtype。无掩码 vm=1 的版本只需在归约指令中省去 `v0.t`。

![相同结果的两种实现方式](<../assets/technical/rvv-sequence.svg>)

图 8-1　VDot 与 RVV 非零路径的静态指令组织。五个 RVV 步骤合计 9 条指令；m1 与 mf2 的区别在乘法和归约配置。

九条指令分别完成长度判断、三次向量配置、一次乘法、两次清零、一次归约和一次配置恢复。VDot 将这些约定的计算与结果处理合在一条指令中。指令数为九比一；实际少用多少周期，还要看依赖等待、配置切换和调度，第 9 章按完整操作测量。

## 8.4 等价验证用例：6 组数据、144 种配置、432 次调用

# 9 延迟测量与软件优化分析

数据已经装入寄存器时，若后一次点积必须读取前一次结果，每增加一次完整操作，VDot 增加 7 周期，RVV-m1 增加 55 周期，RVV-mf2 增加 47 周期。加入加载和存储后，收益随程序安排变化：初版逐点输出基本持平；优化输入加载和 2×2 输入复用后，在相同输出要求下，RVV-mf2 的总周期分别是 VDot 的 1.24 倍和 1.32 倍。

本章先测依赖链：每次把结果交给下一次点积，查看串行执行的完整操作延迟。再固定输入、轮流使用八个目的寄存器，观察多条操作重叠执行时的吞吐。最后加入内存加载、结果存储和共享输入，比较软件安排怎样影响整个任务的用时。每组都在相同输入输出要求下比较 VDot 与标准 RVV。

## 9.1 依赖链延迟：每多做一次点积增加几周期

### 9.1.1 增加链长，分离固定计时开销

读取计数器、设置计时边界和取用最终结果，本身就要花时间。预检中，什么点积也不做的空窗口为 74 周期，只做一次 VDot 的窗口为 81 周期。为减少这些固定步骤的影响，主实验分别连续做 1、8、32 次点积，用“多花的周期数”除以“多做的次数”，计算每增加一次操作的成本。

依赖链使用 v1 作为输入之一，同时把结果写回 v1。第一条 VDot 写出的新 v1，要被第二条读取；第二条写出的结果又被第三条读取。因此，后一次必须等前一次的结果，这就是前后操作的数据依赖。程序分别展开 N=1、8、32 次，输入加载、最后存储和打印放在计时窗口外；RVV 每次需要的配置、清零和恢复仍计入窗口。不同链长的周期差用于计算完整操作延迟。

### 9.1.2 周期、延迟、吞吐和加速比

处理器的 `mcycle` 记录仿真中的周期数，`minstret` 记录退休指令数；主机执行模拟器用了多少秒，另作运行时间记录。设 N 次点积的窗口周期为 C(N)，退休数为 I(N)，正式样本取中位数。表 9-1 给出计算方式。

表 9-1　本章的指标定义

| 指标 | 定义 | 含义 |
| --- | --- | --- |
| 窗口周期 C(N) | 结束 mcycle − 开始 mcycle，单位为周期 | 完整计时窗口的执行周期 |
| 退休数 I(N) | 两次 minstret 读数之差，单位为条 | 计时窗口内退休的架构指令条数 |
| 增量成本 d | [C(N₂)−C(N₁)]/(N₂−N₁)，周期/次 | 每增加一次操作带来的周期增量 |
| 完整操作延迟 L | 真实依赖链中测得的 d | 串行依赖下每次完整操作的周期成本 |
| 延迟加速比 | L_RVV/L_VDot | RVV 与 VDot 的完整操作延迟之比 |
| 增量吞吐比 | 独立批处理中 d_RVV/d_VDot | 操作可重叠时，RVV 与 VDot 的平均周期成本之比 |
| 整窗比 | 同任务、同 N 的 C_RVV/C_VDot | 包含公共开销的同任务整窗周期比 |

例如延迟比 47/7=6.71，表示在本依赖链中，RVV-mf2 每增加一次完整操作所需的周期是 VDot 的 6.71 倍。比较 VDot 自身优化前后时，则计算“原周期/新周期”或减少率 `1−C_新/C_原`。这两种比较的对象不同，后文分别列出。正式样本同时保留中位数和最小～最大值，便于看到运行波动。

## 9.2 CSRRW 写 mscratch 作计时边界

## 9.3 依赖链延迟：7 对 55 / 47 周期

三条路径每次都读取 v1 并把结果写回 v1，后一次操作必须等待前一次的新值。VDot 用一条自定义指令；RVV 每次还要配置、乘法、清零、归约和恢复。表 9-4 列出做 1、8、32 次时的读数。每个点的三个正式样本一致，1→8 与 8→32 两段算出的每次新增周期也一致。

表 9-4　依赖链周期和退休数，单元格为“周期 / 条”

| 路径 | N=1 | N=8 | N=32 | 1→8 增量 | 8→32 增量 |
| --- | --- | --- | --- | --- | --- |
| VDot | 81 / 5 | 130 / 12 | 298 / 36 | 7 周期/次 | 7 周期/次 |
| RVV-m1 | 130 / 13 | 515 / 76 | 1835 / 292 | 55 周期/次 | 55 周期/次 |
| RVV-mf2 | 122 / 13 | 451 / 76 | 1579 / 292 | 47 周期/次 | 47 周期/次 |

7 周期是后一次操作等到前一次结果、经调度并继续执行时，每多做一次完整点积增加的时间。第 6 章的 2 周期只从 VDot 功能单元接受输入算到输出完成。两项测量的起点和终点不同：前者包含后端依赖与调度，后者只看功能单元内部流水。

以 8 次增加到 32 次为例，多做了 24 次。VDot 从 130 增加到 298 周期，多用 168 周期，平均每次增加 168/24=7 周期。RVV-mf2 从 451 增加到 1579 周期，平均每次增加 (1579−451)/24=47 周期。因此两条 RVV 路径与 VDot 的延迟比分别为：

```text
相对 RVV-m1：55 / 7 = 7.86 倍
相对 RVV-mf2：47 / 7 = 6.71 倍
```

三个测量点分别满足 C_VDot(N)=74+7N、C_m1(N)=75+55N、C_mf2(N)=75+47N。公式中的 74 或 75 是固定部分，N 前面的系数是每增加一次操作的周期。用长链减短链，再除以新增次数，可以消去各自的固定部分，无需假定三条实现的固定开销完全相同。

若直接比较 32 次操作的整个窗口，RVV-mf2/VDot 为 1579/298=5.30。这个比值把双方的固定计时开销也算进去，所以小于按新增操作计算的 6.71。后文称它为整窗比，即同一任务整个计时窗口的周期比。

## 9.6 分段点积：中间存储与寄存器归约

分段任务每次读取两组各 1024 字节输入，完成 128 次八项点积。每连续 G 次点积再相加，输出一个段和；G 取 8 或 16。比较两种做法：第一种算完点积就留在寄存器里累加，第二种先把每次完整点积结果存到 scratch 临时区，再读回来相加。第二种额外写 2048 字节、读 2048 字节，最终段和与第一种相同。

G=8 最终输出 16 个完整向量结果，G=16 输出八个。两种组织、三条实现各自比较；计时均包含加载、地址与循环控制、计算、归约、最终存储及末尾 fence/读回。

| 8 | VDot | 2282（2282～2383） | 3031（3030～3169） | 859 / 1388 |
| 8 | RVV-m1 | 2275（2273～2427） | 3394（3394～3440） | 1013 / 1542 |
| 8 | RVV-mf2 | 2321（2320～2454） | 3312（3312～3313） | 1013 / 1542 |
| 16 | VDot | 2240（2240～2296） | 3026（3026～3079） | 843 / 1372 |
| 16 | RVV-m1 | 2360（2359～2438） | 3443（3443～3444） | 997 / 1526 |
| 16 | RVV-mf2 | 2333（2333～2405） | 3263（3262～3312） | 997 / 1526 |

采用寄存器归约后，VDot 在 G=8、G=16 下分别减少 24.7%、26.0% 的周期。两条 RVV 路径也因减少中间搬运而改善。在相同寄存器归约组织内，VDot 相对 RVV-mf2 的整窗比分别为 1.017、1.042，明显小于两种数据组织之间的差异。

## 9.7 输入加载：尾部策略与寄存器轮转

加载实验固定 G=16：做 128 次点积，输出八个段和，三种方案都执行 256 条向量加载。tu 要求保留输入寄存器尾部旧值；ta 不要求保留未用的尾部；ta_rr 在 ta 基础上交替使用 v1/v2、v6/v7，两组寄存器轮流装数据，使下一组输入可以提前准备。VDot 与 RVV-mf2 使用相同改法；VDot 指令本身的 oldVd 规则不变。

本组重新测量 tu 对照，每变体预热五次、取九个正式样本。历史 G=16 的 2240/2333 周期来自不同程序上下文及较少预热，因此本节的优化比例统一由表 9-9 的同批数据计算。

| --- | --- | --- | --- | --- |
| tu | VDot | 2239 | 2238～2241 | 843 |
| tu | RVV-mf2 | 2262 | 2260～2262 | 997 |
| ta | VDot | 1235 | 1231～1236 | 843 |

## 9.8 2×2 小块：共享输入与加载复用

上一组每次点积仍各自加载输入，本组让四次点积共用数据。任务计算 K=256 的 2×2 小块，四个输出分别累加 A0/B0、A0/B1、A1/B0、A1/B1 的点积。每轮处理八个元素，运行 32 轮，共 128 次八项点积；最后保存四个 128 位结果。

若四次点积各自重新加载两份输入，一轮要加载八次。复用方案先把 A0、A1、B0、B1 四个块各加载一次，再组合出四次点积：A0 供前两次使用，A1 供后两次使用，B0 和 B1 也各被使用两次。因此一轮只加载四次，32 轮从 256 条向量加载减到 128 条。VDot 和 RVV-mf2 都采用 ta，B 输入提前按列存好，布局准备放在计时外。

## 9.9 性能结论与适用条件

完整操作依赖链中，VDot 为 7 周期，RVV-m1、RVV-mf2 分别为 55、47 周期，延迟比为 7.86、6.71。固定源、轮转目的时，VDot 平均每增加一次操作只增加 1 周期，体现了专用单元连续处理独立点积的能力。

加入访存后，初版逐点输出程序基本持平；双方采用相同优化后，G=16 加载轮转和 2×2 输入复用的整窗比分别达到 1.24、1.32。其中，预打包的 2×2、K=256 内核中，VDot 用 790 周期，RVV-mf2 用 1043 周期，VDot 耗时少 24.3%。计算单元的优势需要配合加载安排与输入复用，才能保留在完整内核中。

面向边缘 LLM 推理，VDot 可承担 [INT8 线性层](<https://arxiv.org/abs/2208.07339>)中反复执行的点积计算。现有结果说明，在处理器流水线中集成专用点积单元，并配合软件组织输入，能够缩短矩阵小块的计算时间，为量化线性算子提供加速基础。当前收益对应预热后的指令和小内核测量，完整模型的推理收益仍需模型级测试。
